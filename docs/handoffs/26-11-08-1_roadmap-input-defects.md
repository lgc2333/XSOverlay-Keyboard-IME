## 微软拼音与日语输入法无输入

调查初期来源尚未确定。现有 XSOverlay 日志中，日语送键 12 次、拼音 2 次，均没有组字、提交、普通字符或写回回报，也没有焦点获取与 SendInput 失败记录。目标档案与 Win32 前台、焦点正确，故障范围在宿主送键之后、页面写回之前。

[KeyFeeder](../../XSOverlayKeyboardIme/Ime/KeyFeeder.cs) 送键后只排空键消息，[CompositionSession](../../XSOverlayKeyboardIme/Ime/CompositionSession.cs) 随即按组字状态结束会话。先记录实际键消息、TSF 文档焦点与回调次序，再判断是否提前归还前台；现有证据不支持直接增加等待。

进一步隔离验证确认两件事：

- 原生 TSF 空上下文的异步 edit session 返回 `TF_S_ASYNC` 后，键消息排空没有触发回调，进入完整消息泵后才执行。实验未抢前台或发送按键，证明键消息排空不保证异步 TSF 工作完成，但不证明微软输入法现场的具体断点。
- 直接编译生产窗口与会话源码，替换输入法、送键与前台操作。同步 `WM_CHAR` 能立即写回；在 `Send` 返回后再执行相同窗口过程时，字符留在缓冲区，直到下一次 `Send` 才交付。这是插件处理迟到普通字符的确定缺陷，现场关联仍待验证；迟到原生 commit 的对照能立即交付。

原因可由源码复核：[HostWindow](../../XSOverlayKeyboardIme/Ime/HostWindow.cs) 的 `Collect` 只追加缓冲，唯一消费者是 [CompositionSession.WriteThroughTyped](../../XSOverlayKeyboardIme/Ime/CompositionSession.cs)，它仅在 `Send` 内调用。[0032](../adr/0032-deliver-a-late-commit.md) 已覆盖迟到原生提交，普通字符尚没有对应的到达通知。

另发现宿主将全部 `WM_APP` 及以上窗口消息吞掉，包括未知消息。尚未证明输入法依赖这些宿主窗口消息；异步 edit session 实验观察到的是线程消息，不能直接把两者关联为根因。

被动诊断 0.2.0 的定向复现再次确认无输入。`seq=698–1005` 中，微软拼音送键 3 次，微软日语送键 5 次，均在宿主获得前台与焦点后发送，SendInput 返回完整事件数，但键消息排空均为 0，普通字符缓冲均为空，没有组字或提交回调。该段也没有迟到 `WM_CHAR`、`Collect` 或未知 `WM_APP` 以上窗口消息，因此不能用它们解释此次微软故障。

每次送键后逻辑会话结束，但 `batch=True` 时尚未归还前台；实际失焦出现在后续模式动作完成消息的处理内。下一步应把被动观察点移到宿主消息队列与原生 TSF 边界，区分输入提前被消费与 TSF 未产生回调。现有记录仍不支持增加等待或重试。

### 独立宿主的前台归还对照

随后通过浏览器控制普通权限的 .NET 10 独立进程，直接编译生产宿主、会话、送键与档案源码，加载与游戏哈希一致的原生库。实验只给窗口添加字符计数和退出通知，给前台归还添加计数及明确启用的抑制开关，日志只保留计数。没有 Unity 页面、游戏焦点门和真实粘滞释放；原有语言栏状态刷新仍运行。该实验不需要 VR，也没有向游戏部署控制件。

每次只送一个 A，比较后续快照的增量；即时答复只确认入队。每段开始时均无组字，且宿主不占前台。按实际活动档案识别输入项，排除切换后列表重排的影响。

| 输入项   | 原样归还前台             | 仅抑制归还前台               |
| -------- | ------------------------ | ---------------------------- |
| 微软拼音 | 两次均无字符、组字或交付 | 两次均开始组字，组字长度为 1 |
| 微软日语 | 两次均无字符或交付       | 收到一个普通字符，尚未交付   |
| 小狼毫   | 收到并交付一个普通字符   | 未测试                       |

这些区间的前台获取与 SendInput 失败计数始终为零。日语保留前台后收到的字符，在后续取消时才交付；恢复原样后再送 A，字符与交付计数均未增长。拼音实验取消后曾出现组字已清空而宿主仍占前台，下一次取消才归还；该残留状态中送键的成功样本已排除，不能当作原样路径正常的证据。

该干预支持将独立宿主的首键丢失归为插件过早归还前台。它与游戏中的空队列现象一致，但尚未在提权 Mono 游戏进程中重复干预，不能宣称真实 XSOverlay 已修复，也不能把永久保留前台作为修复。

[SendInput 的契约](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)只保证事件插入输入流。原生 [OnEndComposition](../../native/IngameIME_Win32/src/TfCompositionHandler.cpp) 还会先报告组字结束，再异步请求读取提交文本。因此，`Composing=false`、单次队列为空、抬键或已投递消息均不足以证明该键的异步处理已完成。

### 按实际结果收尾的受限实验

另在宿主源码副本中取消送键后仅因 `!Composing` 而 `End` 的分支，让外层消息泵继续运行；普通字符到达时立即取走并交付，再结束会话。原生提交仍走生产回调。原样与实验模式均记录不含原文的事件序列，原生库未改，没有等待、重试或输入完成计时器。

- 拼音原样送 A 无结果；实验模式依次观察到 `send-entry → send-return → preedit(length=0) → preedit(length=1)`。连续送 A、再送 Return 的有效样本中，Return 确实被宿主接管，随后观察到组字结束、长度为 1 的原生提交、会话结束、文本交付与前台归还。该段焦点与送键失败计数未增长。
- 独占桌面时段的新进程日语对照中，原样 A 无字符、无交付；实验模式为 `send-entry → send-return → char-arrival → delivered(length=1) → session-end → restore-attempt`。后续快照确认实际档案始终为微软日语，字符和交付各增加 1，宿主已归还前台，焦点与送键失败计数均为零，不需要取消或下一键。

早先一次前台获取失败、一次回车请求前已经提交，以及日语样本在送键时变回拼音的区间均已剔除。实验与另一输入法调查任务错开桌面操作。实验服务器结束后，子进程经标准输入 EOF 清理宿主，未留下持有前台的实验进程。

这些结果验证了两条输出路径的可行方向，尚未解决无输出按键、异步取消、多字符及 UTF-16 代理对边界。同步 trace 输出也可能影响时序，因此不能直接将该实验副本作为产品修复。实现计划见[六项修复方案](../roadmap-input-fixes.md)。

### 同一上下文的直接 TSF 固定键对照

继续在相同独立宿主 STA 中获取已有线程管理器、焦点文档和顶层上下文，以公开 `ITfKeystrokeMgr` 测试固定 A 的按下与抬起。探针先调用 Test，只有 `S_OK` 且接管才调用 Key；没有 SendInput、未接管字符兜底或队列等待。线程键状态只临时修改 A 的按下位，最后恢复完整快照，不查询或改变输入法转换模式。

微软拼音和日语各一次直接测试均返回 `S_OK`、`eaten=false`，没有进入 `KeyDown/KeyUp`，也没有字符或组字。两次合计尝试数为 2，接管数与错误数均为 0。每项紧接着使用同一档案和上下文执行按实际结果收尾的普通送键对照：拼音在 `send-return` 后报告长度为 1 的组字；日语依次报告 `send-return → char-arrival → delivered(length=1) → session-end → restore-attempt`。各段焦点与送键失败数均为零。

中途尝试在拼音组字期间开启直接模式，被实验保护条件拒绝，随后走取消清理，没有再次直接送键。这段不能用作组字期间直接接口的测试，也没有完成新的拼音提交闭环。清除全部实验模式并确认空闲、宿主不占前台后，才开始日语对照。最后恢复微软拼音并结束自有服务器和子进程。

结果只证明该固定 A 调用没有接管，不能推导全部直接 TSF 路径不可用，也不能把普通字符兜底当作已实现。直接调用仍依赖既有前台获取，不证明后台输入可行。它没有给出短租约可用的完成契约。

持续租约方案还有物理输入的范围问题：当前隐藏窗口只收集可打印字符，没有直接转发物理编辑键与快捷键的路径。安装版 Vuplex 还有独立路径：`NativeKeyboardListener.Update` 读取 Unity `Input.inputString` 及按键状态，`KeyboardManager` 转发到自己的焦点 WebView，最后调用原生 `WebView_keyDown/keyUp`。它与 XSOverlay 内部的 `KeyboardFocus` 不是同一个焦点。

静态代码不能确定隐藏宿主占前台时 Unity 是否继续得到这些按键，也不能确定 Vuplex 是否保留 composer 的焦点。因此不能仅据隐藏窗口断言物理编辑键丢失；原型必须同时检查两个接收端，验证普通字、回车、退格、方向键与 Ctrl+A/C/V，既防丢失也防重复。该方案需要完整输入路由验证，不能仅延长租约后就宣称物理键盘行为不变。

### 聚焦期租约与原生失焦的独立原型

按 [0050](../adr/0050-hold-the-host-focus-for-the-composer.md) 新建普通权限 .NET STA 原型，复用生产输入上下文、会话、档案和送键代码。源码副本只调整租约检查、字符到达通知与焦点观察。`WM_KILLFOCUS` 立即撤销资格并放弃旧前台，随后保留原窗口处理；不发送 Escape，不修改输入法模式，也不调用激活开关代替失焦。该原型没有 Unity、Vuplex 或真实 composer，页面只是实验控制面板。

微软拼音的有效对照先确认档案激活成功，再送固定 A。后续快照为组字长度 1、宿主持有前台、尚未交付。通过桌面点击实验进程的另一个窗口使宿主真实失焦，随后记录资格已撤销、组字结束、原生提交与交付各增加一次，交付内容与固定 `a` 相等；最终宿主不在前台。没有发送 Return 或 Escape，该结果符合用户报告的拼音失焦提交原始编码。

在上述失焦后，直接调用会话尝试再送 A，目标检查拒绝，字符与交付计数不变，前台没有被抢回。小狼毫首轮也通过失焦后拒绝送键，但该样本原样送出 A，没有进入组字，不能据此确认其组字时不提交的基线。后续小狼毫区间出现未受控字符增长，未作为固定按键样本。

本轮还出现两次显式聚焦获取失败，均未继续发送或重试。没有记录原生返回与前后台即时快照，不能归因于系统拒绝或被夺回，也不能将它等同于真实 XSOverlay 的首次聚焦缺陷。

原型的焦点期编号只用于日志，尚未给排队按键和提交加上旧期身份。因此失焦后拒绝按键不等于快速重新聚焦后也能隔离旧按键；原生交付回调成功也不等于真实页面已接受迟到提交。物理编辑键、快捷键、代理对与 Vuplex 双路输入仍待验证。

构建无警告或错误，独立审查指出的信号退出管道泄漏已修复。运行前记录的 11 个实验文件与产物哈希在运行后均匹配。退出时已切回最初的小狼毫，无组字、无宿主前台；子进程退出码为 0，临时服务器、端口监听与窗口均已清理。SteamVR 未启动，产品源码和游戏安装产物未改。

### 失焦提交与页面撤销对照

使用当前生产页面源码在内存中构建 bundle，在隔离 Chromium 158 中加载。组字后使输入框真正失去 DOM 焦点，`insertText` 返回 `focus-lost`，随后页面发出取消请求。模拟旧文本回调时，重新聚焦后的新预编辑 `b` 被旧文本 `a` 替换；重建同名输入框后，旧回调也会写入新节点。这些固定回调注入只证明接口未携带来源身份，没有模拟真实 TSF 调度。

普通文档中的对照显示，`setRangeText` 可在另一个输入框获焦时写入原框，也不自动发出 input 事件，但 Ctrl+Z 无法撤销这次改动。用户拒绝这一撤销例外，要求继续调查；只有保留撤销确实不可行时，才考虑统一丢弃失焦预编辑。没有新增 ADR，也未修订 [0008](../adr/0008-inserttext-writeback.md) 或 [0050](../adr/0050-hold-the-host-focus-for-the-composer.md)。

最初的多页面测试中，两页均报告 `document.hasFocus()=true`，不能充当后台样本。后续改用独立 Chrome 156 窗口，并通过 [CDP](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Emulation.pdl) 显式关闭 `setFocusEmulationEnabled`。五种对照均确认 A 的 document 焦点为 false、B 为 true，然后检查写入目标、input 事件和撤销、重做。

保留 composer 为 activeElement 的后台样本得到 `p → pa`，回到 A 后 Ctrl+Z 得到 `p`，重做恢复 `pa`。先把 DOM 焦点移到按钮的样本也能后台写入，activeElement 不变；是否再次设置选择范围不影响本样本结果。该路径 Ctrl+Z 会连同先前的 `p` 一起撤销，重做恢复 `pa`，因此只证明原生撤销栈有效，不证明提交具有独立撤销单元。

另一个输入框持有 DOM 焦点时，仅给 composer 设置选择范围仍将 `a` 写入另一个框。后台临时将 DOM 选择移至 composer、写入再恢复原元素的对照，将 `a` 正确写入 composer，另一个框的 `q` 保留，撤销为 `p`、重做为 `pa`。这没有经过生产焦点观察器，不能据此认为临时选择已能安全接入。

后续 headless Chromium 158 对实际焦点观察器和完整生产 bundle 运行 12 项同步 DOM 聚焦、裸写入、恢复的对照，并增加延后恢复的阳性控制。八项空闲对照中，写回为 `pa`、另一个框保持 `q`、撤销为 `p`、重做为 `pa`，没有激活或取消桥消息。页面仍活动时，观察器的本地回调同步变为 true、下一任务变为 false，完整页面的切换按钮也短暂挂载。人工派发 window blur 后，这两项保持 inactive；该人工事件并未使 `document.hasFocus()` 变为 false，不是原生后台样本。

四项预编辑对照在写入前确认插件仍报告组字，正文为 `pni`、下划线可见，且没有预先取消或调用 idle。裸写入得到 `pnia`，随后 selectionchange 在约 1.5–3 毫秒内触发现有保护并请求一次取消，不能把这当成有效提交路径。撤销回到 `pni`、重做为 `pnia` 只证明这次浏览器编辑可撤销。本轮同步对照未报告宿主激活；页面活动时，聚焦后延后一个任务才恢复的阳性控制，确实收到 composer-active 与 composer-inactive。没有覆盖全部异步形式或真实后台，正常提交还需处理原输入期预编辑。

自动运行的原生观察器记录了相同的写回前后 HWND/PID 和区间内零前台回调，但这些快照实际属于桌面壳进程，不能称为 B 窗口的前台对照。随后使用电脑操作工具明确选中并激活 B，核对原生窗口标题属于固定实验 B、A 的 document 焦点为 false、B 为 true。该有效样本中后台写回成功，原生前后均为 B，区间无前台回调；回到 A 后 Ctrl+Z 为 `p`，重做为 `pa`。切回 A 的真实前台回调也被观察到，随后同线程解除钩子成功。

后续按钮失焦样本的原生前台已被用户操作切到其他窗口，未满足 B 前台控制条件，排除该样本。另一轮电脑操作被误按 Escape 中断，未当作产品失败。实验 Chrome 窗口已关闭，观察器退出码为 0，钩子已解除；SteamVR 未启动。

真实释放代码先释放虚拟键，再调用 Vuplex `IWebView.SetFocused(false)`，随后发送 `KeyboardInputFocusReleased`，页面收到后调用原元素 `.blur()`。原生失焦事件与页面通知跨 IPC，静态顺序不能保证页面接收顺序。Vuplex 的 `ExecuteJavaScript` 调用路径没有重新设置焦点，原 `SendKey` 则会调用 `SetFocused(true)`，因此后者不能作为后台写回的验证入口。

已有真实 Vuplex 诊断两次记录 `focusout → page-blur → composer-inactive`，activeElement 仍为 composer、`documentFocused=false`，证明其能够进入背景 document 状态；日志未绑定触发 API。真实 Vuplex 后台写回、撤销、桌面前台与生产监听器的组合仍待验证，桌面 Chrome 的成功不能替代该边界。

### TSF 迟到提交的来源与范围对照

生产 [CompositionHandler](../../native/IngameIME_Win32/src/TfCompositionHandler.cpp) 未保留开始组字时的 composition 身份。结束后将同一 edit-session 对象排队，执行时读取并清空整个持久上下文。shim 与托管回调只保留字符串，根入口再排到 Unity 队列，写回时重新寻找当前页面。给回调发生时的当前输入期编号不能恢复原来源。

独立原生探针创建合成 TSF 上下文，不显式创建窗口，不获取前台，不发送按键，也不选择输入项或查询模式。旧组字的固定文字为 `a`，来源编号为 1；旧组字结束后，在同一上下文启动文字为 `b` 的新组字，将当前编号改为 2，随后执行旧的异步读取请求。

最早的探针按第一个结束回调选样，可能选中 `SetText` 的隐式组字，不能证明 composition 来源。后续改为在 `OnStartComposition` 保存规范 `IUnknown` 身份和来源，结束时按同一身份匹配，并核对两次显式启动的返回对象。每个请求按值持有来源、范围和共享状态，退出先撤销活动资格再释放 COM，未保留主函数栈引用。

按 [ITfClientId](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nn-msctf-itfclientid) 为合成生产者和应用分配不同客户身份后，应用能读出预先固定的旧范围 `a`，而全文为 `ab`。将旧范围改成 `x` 后全文为 `xb`，清空旧范围后全文为 `b`；新组字范围始终为 `b`，未收到它的结束回调。该合成对照支持范围隔离，但不是快速重新聚焦或微软输入法实测。

单变量对照补齐了限制：相同排队位置下，共用客户身份的旧范围改写返回 `TF_E_RANGE_NOT_COVERED`，独立客户身份成功，符合 [SetText](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfrange-settext) 对活动组字所有者的约束。独立客户在结束回调内请求异步会话也成功，但该样本不能升级为所有输入法上的调度保证。

范围不是不可变快照。不固定范围重力时，保留范围会延伸到新插入的 `b`，后续旧范围操作也影响新组字。成功样本使用合成生产者已经持有的有效 write cookie 固定边界；尝试在结束回调中直接使用创建上下文时的 cookie 则返回 `TF_E_NOLOCK`。因此生产端何时取得合法 cookie、如何及时保留最终范围，仍是具体待验证项。

同一个 composition 在匹配的结束回调中 `GetRange` 成功，结束返回后再调用则为 `E_UNEXPECTED`，符合[公开文档](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcompositionview-getrange)。不能等异步读取时才从已结束的 view 取范围。

后续合成对照将两个组字分到两个生产者编辑会话。旧组字结束后，通过已注册的 [OnEndEdit](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itftexteditsink-onendedit) 取得只读 cookie，固定旧范围重力返回 `S_OK`。随后先排入创建新组字的会话，再排入应用读取会话，保留旧来源为 1、当前编号为 2。读取、改写和清理旧范围均成功，新组字保持 `b`，退出码为 0。此实验验证了不借用输入法 write cookie 的公开入口，但不覆盖两个组字在同一编辑会话中结束和启动，也没有验证实际输入法的回调时机。

新增四种合成对照令旧组字从空范围开始，再增长为 `a`，分别保留开始时与结束时的克隆。两次生产者编辑之间固定边界时，两种克隆都只清除旧 `a`，保留新 `b`；同一次编辑内先结束旧组字再启动新组字时，两种克隆均在 `OnEndEdit` 前增长为 `ab`。此时固定重力虽返回 `S_OK`，随后清除仍误删 `b`。新 composition 的 `GetRange` 仍成功，不能把内容被删除写成组字已终止。该失败否定了原型中“等到编辑结束再固定足够早”的假设，不是现有产品缺陷的复现。

进一步在匹配的结束回调内请求 `TF_ES_SYNC | TF_ES_READ`，用返回的有效 cookie 读取并固定私有克隆。四种合成对照均返回 `S_OK`，旧范围保持 `a`，全文为 `ab`，异步清除后只剩新组字 `b`。该合成环境没有窗口、前台、按键、档案激活或模式查询。[RequestEditSession](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcontext-requesteditsession) 对同步请求有条件限制，不能将此结果当作任意真实回调中的保证。

随后运行独立 .NET STA 宿主，临时原生库只在真实 `OnEndComposition` 中复制私有范围，增加同步只读观察，保留原异步提交路径。微软日语的固定 A 先产生长度 1 的组字，随后在仍持有前台时结束；`GetRange`、克隆、同步请求、会话、读取及重力设置全部为 `S_OK`，读取内容与固定 `a` 相等。另一空范围结束回调也成功，原路径最终提交并交付一个 `a`。这些事件发生于真实桌面失焦和退出之前。拼音与小狼毫本轮仅交付普通 `a`，没有组字，不能计为结束回调验证。

观察没有新增转换模式查询、激活变更或强制收尾；上游原实现仍包含它自己的模式读取与释放时的终止组字路径。私有克隆在结束回调返回时释放，实验只证明此真实路径能及时获得读取 cookie 和固定边界，不证明长期保留范围、快速重新聚焦或新旧组字隔离。审查后已更正构建前生成的产物哈希清单。退出前恢复最初的小狼毫，子进程退出码为 0，端口与窗口均已清理，未部署到游戏，SteamVR 保持关闭。

后续独立宿主将私有克隆保存在 COM edit-session 对象中，结束回调内同步固定后，再排入异步只读观察。直接选择日语和切到拼音的固定 A 只产生普通字符，未计为组字验证；从拼音切回日语后，固定 A 产生长度 1 的组字及结束回调。同步读取、固定边界均为 `S_OK`，异步会话状态为 `TF_S_ASYNC`，实际执行时 RAII 标记确认结束回调已经返回，读取仍为固定 `a`，原提交随后正常交付一次。另一个空组字的保留范围也成功读出空值。

新观察排在原异步清理之前，改变调度，不能证明未加观察时的自然顺序、清理后的范围、新组字隔离或快速重新聚焦。每次最多读取 32 个 UTF-16 code unit，只输出固定 A 相等性与长度，不记录输入原文。运行前后源码与产物哈希全部匹配，退出前恢复最初的小狼毫并释放前台，子进程退出码为 0，端口与窗口已清理；本轮没有启动或关闭 VR 进程，也没有部署到游戏。

另对临时宿主的 `TakeTyped` 做了纯缓冲检查：普通前缀可先交付，尾部单个高代理保留，低代理到达后完整代理对一起交付，两个完整代理对也不拆分。没有窗口、消息或输入法参与，且只验证临时代码，不证明生产缓冲已修复，更不证明跨输入期的普通字符来源。

### 普通字符的消息来源对照

生产宿主在两个消息泵中都先调用 `TranslateMessage`，再派发 keydown，普通字符缓冲只有 UTF-16 内容。[TranslateMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-translatemessage) 将字符消息投递到调用线程的队列；[WM_CHAR](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-char) 明确不保证按键与字符一一对应。收到字符时使用当前输入期，或按一个 keydown 消费一个来源编号，都没有完整来源契约。

独立 Win32 窗口在点击固定测试按钮后，核对本窗口持有前台与键盘焦点，再用 `SendInput` 注入固定 A 和两组固定 UTF-16 代理对。没有 TSF 上下文、档案切换、模式查询或钩子。消息泵分别在翻译旧 keydown 后、字符派发前改变逻辑输入期，并在高低代理派发之间再次改变；这模拟应用编号边界，不是真实桌面失焦。

普通 A 的 keydown、keyup 记录 `ExtraInfo=17`，生成的 `WM_CHAR` 为 0，字符发布时间晚于源按键。相同标记 34 的代理对、分别使用标记 51 和 68 的高低代理也得到字符标记 0，字符时间与对应按键不同。A 从注入时的逻辑输入期 1 跨到派发时的 2；两组代理对的高低代理分别在 3、4 和 5、6 派发，高代理仍属于各自注入时的编号。三个注入批次全部成功。由此可以否定本机这条路径通过 `ExtraInfo` 或相同时间戳反查来源的方案；它不证明所有输入法输出的形式。

[KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput) 的标记只明确关联按键，[GetMessageTime](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessagetime) 只给最后取出消息的时间，均未提供 composer 身份。无标记的物理输入、多对多转换、IME 后续字符与跨来源代理对仍待处理，完整代理对缓冲本身不能解决归属。实验完成后窗口自行关闭、进程退出码为 0，未修改游戏或系统设置。

代码核对还发现，[HostWindow](../../XSOverlayKeyboardIme/Ime/HostWindow.cs) 的窗口过程通过静态当前对象路由，未按传入 HWND 找接收对象，销毁任意宿主窗口又会结束 STA 消息泵。原生 TSF context owner 返回构造时固定的 HWND，激活关联也沿用它；提交则从共享上下文异步读取，回调只有字符串。因此增加窗口编号本身不能解决来源，轮换窗口也不是已有上下文的直接替换操作。公共 [AssociateFocus](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfthreadmgr-associatefocus) 只规定窗口与 document manager 的关联，不保证旧窗口或旧上下文已经没有结果；[IsWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindow) 还明确提醒 HWND 会复用。该结构方案尚未选用。

无交互的独立 Win32 对照创建两个隐藏且不可激活的窗口，不显示、不聚焦、不注入系统输入，也不创建 TSF 上下文。明确投给旧窗口的字符，在应用逻辑目标变成新窗口后仍派发到旧 HWND。翻译手动投递的 keydown，以及默认处理手动投递的 `WM_IME_CHAR`，本机也将衍生字符派发到旧 HWND；同一个 HWND 内改变逻辑输入期则无法从字符恢复旧编号。销毁旧窗口后，该样本不再取出已投递字符，不能据此建立安全销毁或完成契约。两窗口始终不可见，运行前后桌面前台未变。第一次合成 keyup 缺少过渡位，产生重复字符，已排除；补齐 keyup 的过渡、先前状态及扫描码位后采用结果。该对照只验证接收身份，不能代替真实键盘目标选择、失焦或 TSF 迟到提交。

另检查了把原 MSG 的 HWND 换成私有字符接收窗口，再提前排空字符的候选。公开 [TranslateMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-translatemessage) 契约没有保证这种重定向与真实键盘、死键或 IME 的原路径等价，提前消费字符也改变了它与原 keydown 窗口过程的顺序。生产 TSF 路径没有 IMM 实现中的 `WM_IME_CHAR` 抑制，其他消息仍交给默认窗口过程。候选既不能覆盖所有潜在字符来源，也不能补出物理 keydown 已缺失的输入期，未据此新增实验或采用该机制。

### 独立窗口与 TSF 文本存储的候选对照

使用未修改的原生 C ABI 库，在单个 STA 创建两个隐藏、不可激活的窗口及各自上下文，通过公开 `EnumDocumentMgrs`、`GetTop`、`GetActiveView` 与 `GetWnd` 匹配接收者。每个原生回调携带独立且稳定的 user 标记，不使用托管静态当前对象。探针没有显示或聚焦窗口、发送系统按键、选择输入档案或查询模式；原生库保留它自己的构造与激活行为。

合成生产者按独立客户身份在旧上下文启动 `a`、在新上下文启动 `b`，再结束旧组字。原生库原样执行全范围读取和清理，只向来源 1 提交固定 `a`；新上下文仍为固定 `b`，有一个活动组字且没有提交。结束新组字后，来源 2 只提交固定 `b`。全范围清理在各自上下文产生了额外隐式组字，探针统计这些回调，随后用公开异步会话核对两边文本为空、活动组字为零，再释放对象。该等待只覆盖已知测试请求，不是任意输入法的收尾契约。

两份已使用并转为原生未激活的上下文，与 30 份额外初始未激活上下文，共 32 份参与资源对照。最终记录增加 30 个 USER 对象、0 个进程句柄和 90,112 字节私有分配，前一次完成样本为 102,400 字节。初次 TSF 初始化另有较大开销；这些是进程级分配采样，不是单个对象大小，也不是已使用过的真实输入法上下文成本。释放窗口、原生对象、DLL 和 COM 后，USER 对象回到进程基线，句柄与私有分配未回到基线，不能认定无泄漏或据此决定保留数量。

最终实验退出码为 0，32 个窗口均不可见且保留不可激活样式，前后台窗口身份未变。它证明合成编辑中的上下文隔离与原生回调来源可行，不覆盖真实 IME、默认失焦、模式保持、快速重新聚焦或 XSOverlay。尚未采纳每输入期新建窗口和上下文，也没有新增 ADR；回收时机与真实输入验证仍是前置条件。

### 独立上下文的真实输入与焦点转移

后续独立 .NET STA 原型使用两个屏幕外接收窗口，各自创建未修改的原生上下文，C ABI 回调携带固定 user 标记，字符消息按实际 HWND 路由。两个上下文在测试前都已激活，试验期间不改变激活状态，不发 Escape、Return 或强制提交。原型未额外查询或切换中英模式，原生库保留自身内部读取。电脑操作工具选择并点击同一进程的可见测试窗口，随后明确聚焦接收者；原型没有操作游戏或用户文档。

有效拼音样本中，来源 2 已有长度为 1 的组字。同一操作先聚焦来源 1，再发送固定 A。来源 2 的结束回调发生时，系统前台与键盘焦点已是来源 1；随后提交仍通过来源 2 的 user 标记交付一个固定小写 `a`。来源 1 再开始自己的长度为 1 的组字，之后失去原生焦点时，也在两个接收窗口均不占前台的情况下向来源 1 提交一个固定 `a`。该过程保留默认窗口处理，没有以停用上下文代替失焦。

旧提交先于新组字开始，因此这份真实样本证明跨焦点回调的来源保持，不证明旧提交与新组字重叠时的隔离。此前合成编辑覆盖了后一种顺序，两者的范围不能合并。来源 2 的结束通知还早于其 `WM_KILLFOCUS` 窗口回调，说明焦点转移内存在重入；送键资格不能只读缓存标志，还须在发送前核对实际前台与键盘焦点。`SendInput` 与核对之间仍存在系统焦点竞争，不能宣称原子指定了接收窗口。

日语固定 A 的组字、结束与提交均回到来源 2，但它在焦点转移前已经自行结束，不计入组字失焦验证。拼音也出现过仅交付普通字符的样本，按实际回调分类。小狼毫固定 A 仅交付普通字符，没有进入组字，仍不能验证用户报告的不提交基线。焦点离开实验后的两次请求被拒绝，没有补发或重新获取前台。

原生源码还暴露了两个候选方案约束。[候选列表监听](../../native/IngameIME_Win32/src/TfCompositionHandler.cpp)订阅共享线程管理器的 UI-element source，未按所属文档过滤，多个存活上下文可能重复收到同一候选通知；此次没有使用候选回调证明来源。[销毁路径](../../native/IngameIME_Win32/src/TfInputContextImpl.cpp)也没有待处理会话的完成屏障，组字结束并不等于可释放。原型将窗口、原生对象、回调及来源记录保活到独立进程退出，没有用固定等待决定回收，也没有验证产品内安全回收。

所有带线程字段的原生追踪事件均在同一托管 STA 线程回报。实验退出前核验活动档案恢复为初始小狼毫，子进程退出码为 0，临时服务和窗口已清理。没有测量已使用真实输入法上下文的长期保留成本，没有验证模式保持、物理编辑键、Vuplex 或 Unity；双窗口与文本存储仍是候选，尚未形成产品决定。

### 多上下文的公共接口约束

候选列表的公开 [GetDocumentMgr](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcandidatelistuielement-getdocumentmgr) 可以返回所属文档，比较时须将双方接口规范化为 `IUnknown` 身份。它不是所有输入法都实现的保证：微软 [SampleIME 的实现](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/IME/cpp/SampleIME/CandidateListUIPresenter.cpp#L539-L544)返回空指针与 `E_NOTIMPL`，失败或空值不能解释为当前焦点所属文档。

[UI-less 契约](https://learn.microsoft.com/en-us/windows/win32/tsf/uiless-mode-overview#the-flow-chart-of-uilessmode)允许内容直到首次 Update 才就绪，不能只在 Begin 判定一次。[GetUpdatedFlags](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcandidatelistuielement-getupdatedflags)的 `TF_CLUIE_DOCUMENTMGR` 又明确允许目标文档改变，因此必须重新确认更新后的归属。End 只携带元素 ID；当前资料未保证此时仍可重新查询元素，路由只能依据该活动元素先前已确认的关联，并在 End 清除。没有查到 ID 结束后永不复用的保证，不能把它当作永久来源身份。真实三款输入法的返回值仍待采集。

原生对象释放与结果完整性也是两个问题。[AssociateFocus](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfthreadmgr-associatefocus)不增加文档引用计数，销毁前须移除或恢复窗口关联，并独立管理文档所有权。每次异步编辑请求可以持有自己的状态，避免原生 owner 被销毁后再访问；这只能证明内存安全，不能证明所有实际迟到提交已经交付。[RequestEditSession](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcontext-requesteditsession)对待处理异步请求的顺序承诺不是输入法永久不再产生结果的屏障。尚未证明在保留全部迟到提交的同时，能按焦点期有界回收上下文；未据此增加超时、丢弃或停用兜底。

### 原生 COM 身份与最终释放缺陷

生命周期审查另确认了随插件打包的 IngameIME 原生依赖缺陷。上游 `COM_DEF_BEGIN` 在查询 `IUnknown` 时返回完整对象指针，但其首基类是含虚析构的 `ComObjectBase`，真正的 COM 接口位于另一个地址。同继承结构、同宏的 MSVC x64 对照中，四个接口返回同一个错误地址，首个 COM 接口偏移为 16，两个地址的虚表首项不同；直接编译实际 `CompositionHandler` 头文件的布局报告也确认该偏移。没有调用错误 `IUnknown` 的虚表来触发崩溃。

第二处是 `InternalRelease`：计数归零时 `delete this`，随后返回已释放对象内的 `ref`。直接编译上游实现的 AddressSanitizer 对照检出第 13 行的四字节 `heap-use-after-free`。临时对照改为选择明确的 COM 接口身份，并在删除前保存剩余计数后，两项检查通过，最后一次 Release 返回 0。

用户授权 fork、修复并验证后，已发布 [fork 修复提交](https://github.com/lgc2333/IngameIME_Win32/commit/a95d660c1d5b2ba0b0e933266df4e23e5f6c7232)。三个生产 handler 明确选择自己的标准 COM 接口身份；C ABI、输入处理及 TSF 会话策略保持原有行为。新增[原生回归](../../native/IngameIME_Win32/tests/ComObjectBaseTests.cpp)覆盖多接口身份、通过查询所得接口调用、失败查询、引用保活及恰好一次销毁，普通与 AddressSanitizer 构建均通过。根构建和 CI 接入 CTest，子模块源与许可证来源记录指向 fork，并保留上游基点。

修复库还通过原有独立 TSF 合成对照：旧来源只提交 `a`，新来源保留活动组字 `b`，随后独立提交；窗口始终不可见，前台未变。它验证修改后的库仍支持该原生路径，不覆盖真实按键、Vuplex 或提权 XSOverlay。尚未部署到 XSOverlay，也未证明这两处缺陷导致前述六项现场症状；它们不解决 raw owner 的异步存活期、候选归属或上下文回收契约。

## JIS 专用键

[KeyStrokeReader](../../XSOverlayKeyboardIme/Takeover/KeyStrokeReader.cs) 在组字期间按键名白名单映射，无映射时吞掉，空闲时只接管单字符。有效的 JIS 专用键因此也无法按 [0048](../adr/0048-route-jis-ime-keys-through-the-host.md) 的目标规则送达。

安装版布局注明 `Keycodes are actually ScanCodes`，三键原始值分别为無変換 `7B`、変換 `79`、平/片假 `70`。XSOverlay 将这些值按十六进制扫描码转换，失败时保留原值。当前系统已加载的日语与美式布局均将扫描码 `0x7B` 映射为 `235`，`0x79` 与 `0x70` 返回零。真实页面模块沿用宿主给出的数值，`webValue` 则沿用日文标签，包括平/片假的 `<br>`。

历史现场已捕获無変換 `values=[235] web=無変換` 和平/片假 `values=[70] web=カタカナ<br>ひらがな`。変換尚无现场事件，`values=[79]` 来自当前系统映射与真实模块的离线重建。直接运行 XSOverlay 枚举解析可复核 `70 → VK_F`、`79 → VK_O`、`235 → 未命名数值 235`，但页面焦点路径优先使用 `webValue`，因此尚未闭合现场 `f` 的完整输出路径，無変換的 `a` 更不能用 `7B` 的十进制猜测解释。

插件漏接管有效专用键与上游原码转换是两层问题。[0048](../adr/0048-route-jis-ime-keys-through-the-host.md) 只修前者，不能使当前安装的 `70/79/235` 自动成为 `KANA=0x15`、`CONVERT=0x1C`、`NONCONVERT=0x1D`。`70/79` 已有转换失败后保留原值的证据；`235` 是系统实际映射，尚未验证其 OS 事件与输入法解释，不能直接判错。实现应按有效原生键码识别，避免 `KANA/HANGUL` 同值枚举别名影响，保留原有组合键规则，不按标签猜测并补键。

后续被动诊断 0.7.0 整合前台观察与 JIS 来源追踪，尚未部署。原诊断没有记录原模拟器的普通键，也没有将 `235` 列入页面原值的安全分类。新版补齐这些分类，观察插件判定和 `KeyboardInputFocusManager.SendKey` 的固定参数类别；所有其他文本仅记长度或 other。

每次相关 `InputManager.HandleKeypress` 同步调用获得线程局部编号，最终清理恢复上一层编号，异常保持原行为。编号不能跨线程传给宿主，也不能标识异步 DOM 消息。页面另观察 keydown/up、beforeinput、input 和组字事件，使用固定类别而不记录原文。它们只提供时序线索，单键复现时仍须核对完整链路，不能直接按到达次序认领事件。

游戏同款 Unity Mono 的替代原函数检查验证编号嵌套恢复、跨线程隔离、参数不变、原异常传播及其他 prefix 取消原调用时的清理。独立 Chromium 检查验证监听不阻止正常打字、只安装一次、未知文本不经桥发送，以及键盘、指针、焦点和 DOM 观察的移除。组字分类采用合成事件，不是微软输入法结果。

独立审查还发现原诊断日志输出可能抛异常，影响被观察函数。新版只计数输出失败，不将异常抛回产品调用。直接加载新诊断产物、使用同款 Mono 和故意抛异常的日志输出端验证后，替代函数的 true、false 和原异常均保留，调用次数为三。该检查验证日志故障隔离，不证明真实游戏送键正常。

## 失焦时 Alt+Shift+F

最后三次对照已将 Alt 快捷键失效定位到 XSOverlay 原始模拟器的按键编码与目标程序解释的边界；用户另报的状态反转尚未再次复现。[KeyboardOverlayScope](../../XSOverlayKeyboardIme/Game/KeyboardOverlayScope.cs) 使用 XSOverlay 的键盘焦点与所属浮窗判定接管，[页面焦点](../../web/src/composer-focus.ts)是另一状态。仅凭 composer 外观失焦，不能证明插件已退出接管。

下一步同时记录两种焦点与目标收到的按键，并对照物理键盘、插件停用和插件启用。确认未接管后，再调查 XSOverlay 原始修饰键链路、系统语言热键与目标快捷键配置。

进一步离线验证链接了生产 Harmony 补丁，并用 stub 接收送键调用。稳定失焦时，Sticky、Toggle 与实际双击的 `Sticky → Toggle` 序列在补丁前后相同，均保留 Alt、Shift、F。若 Alt 按下后释放游戏焦点，XSOverlay 会清空虚拟键，后续 Shift 与 F 的确可能成为大写 F；尚未证明现场发生过该状态切换。

本机旧式语言切换热键已禁用，VSCode 用户快捷键文件没有覆盖 Alt+Shift+F，安装版默认格式化绑定存在。扩展覆盖、编辑器上下文与 OS 最终收到的事件仍未排除，不能据此把问题归给 XSOverlay。

现场反馈进一步明确：初始状态正常，Shift 与 Alt 都双击进入保持后遇到问题；Alt 保持可用，粘滞时出现页面状态与实际按下情况反向，重新聚焦并失焦 VR composer 后输入恢复。这是用户报告的触发条件，尚未由状态快照完整复现，不能简化为所有 Alt+Shift+F 都失败。

原页每键的第一次点击立即发送 Sticky，250 毫秒内第二次发送 Toggle。游戏将键从粘滞集合移入保持集合，发送序列为 Down、Down，解除保持时发送 Up。`seq=1302–1333` 与 `seq=1392–1423` 两段符合该路径，中间没有页面重建或焦点变化。整个诊断会话至 `seq=1840`，修饰键转发到插件宿主的成功次数为 0；失焦路径均回到游戏原模拟器，尚无插件交换边沿或两条发送路径混用的证据。

现有诊断采样通用 VK 的 `GetAsyncKeyState`；游戏亮灯读取左右键的 `GetKeyState`，再与系统粘滞、系统保持、网页粘滞、网页保持四个内部集合取并集。几次 F 之前的异步快照均显示 Alt 与 Shift 已按住，但未记录上述分项和目标程序收到的事件，因此不能排除用户报告的反转。焦点获取与真正失焦都存在释放虚拟键、清空集合的路径，能够解释恢复机制，但恢复前快照已为未按住，不能据此确定故障来源。

下一轮只需被动记录上述四个集合的修饰键成员、左右 Alt/Shift 的同步与异步状态、宿主发给页面的左右键状态，以及 Sticky/Toggle 与 Down/Up 的次序。`Forward` 的后置日志发生在原模拟器送键之前，不能把它当成送键后的 OS 结果。暂不要求继续在项目文档中复现；本轮误输入发生后的路线图现已核对恢复。

## 回车无反应

旧的组字回车丢焦已定位为插件遗漏原页提前发送入口，见 [0047](../adr/0047-route-page-consumed-return-through-the-host.md)。本次无反应已确认另有插件路径错误。

[回车路由](../../web/src/composer-return.ts)先阻止 VR 原始按压，再加载原页按键模块，成功后才请求宿主。[模块地址](../../web/src/native-keyboard-input.ts)使用 `/UserInterface/Default/Keyboard/js/keyboard-input.js`，而真实键盘页从 `/apps/UserInterface/Default/Keyboard/Keyboard.html` 加载。现场只读 GET 已确认前者返回 404，补上 `/apps` 后返回 200。加载失败后没有请求宿主，已阻止的原事件也不会重放；缓存的失败 Promise 让后续 VR 回车继续失败。[回车音效模块](../../web/src/return-feedback.ts)也有相同地址错误。

三项[回车浏览器测试](../../web/tests/composer-return.spec.ts)通过；[测试服务器](../../web/tests/server.mjs)仅复用安装版按键与音效模块，发送仍为 mock，不覆盖真实宿主往返和原页发送链路。

进一步隔离验证直接加载安装版按键、语音输入框视图与发送模块，再注入生产页面脚本。最初 DOM Enter、pointer、touch 各验证空闲与组字，共六项通过，但该服务器同样错误地提供了无 `/apps` 的地址。按真实路由重跑后，DOM Enter 两项通过，pointer 与 touch 四项均返回零请求、零发送，并记录 `Return input failed`。只在调查脚本的内存 bundle 中补全模块地址，六项全部通过。宿主答复、焦点释放与最终发送端仍为模拟边界，产品代码尚未修改，修复后仍需 VR 验证。

## JIS 出现中英切换按钮

来源为插件页面。[switch-key](../../web/src/switch-key.ts)只判断焦点、图标与按键结构，没有物理布局条件。[0012](../adr/0012-synthesized-modifier-key.md)明确要求 JIS 不插入按钮；取代它的 [0028](../adr/0028-mirror-the-ime-language-bar-item.md)没有保留该限制，[0042](../adr/0042-hide-the-switch-without-an-icon.md)和 [0046](../adr/0046-place-the-switch-beside-left-alt.md)也未补回。

历史提交 `f64c1f9` 将按钮改为语言栏项并移除术语表中的 JIS 限制，`cbb0d06` 随后新增布局按钮脚本，自首次实现就没有 JIS 判断。没有找到明确要求 JIS 显示的独立决策，也不能从提交记录判断是否经过用户确认。

XSOverlay 布局数据的 `keyboardFormat` 区分 ANSI、ISO、JIS；这是页面的物理布局，不是当前输入法的语言。已确认通过 [0049](../adr/0049-hide-the-input-mode-switch-on-jis.md) 修订 0042 与 0046 的可见性范围，保留后续决定的其他机制。恢复限制时应分别验证 JIS 配中文输入项、ANSI 配日语输入项，以及布局重建后的按钮数量和空格宽度。

## 首次聚焦后切换无效

新增问题已完成初步来源定位。真实会话 `seq=47–48` 首次聚焦 composer，`seq=58/62` 的档案请求已到页面入口与宿主 STA；`seq=63–65` 取前台失败，前台线程仍为 `24148`，宿主线程为 `32992`。第二次 `seq=75/79/82–84` 同样失败，实际输入项仍为小狼毫。

`seq=88–104` 发生 composer 失焦、游戏释放键盘焦点与再次聚焦，随后第三次相同请求在 `seq=122–123` 取得宿主前台与焦点，`seq=135` 确认微软拼音已激活。失败发生在 [ActivateProfile](../../XSOverlayKeyboardIme/Ime/CompositionSession.cs) 的前台门槛，尚未调用输入法档案激活 API，不能归为输入法拒绝切换。

该记录没有桌面点击标记、`SetForegroundWindow` 原始返回值、前台窗口所属进程或最后输入时间，因此只能证明取前台失败，不能区分系统拒绝与其他窗口立即夺回，也不能证明桌面点击的因果作用。下一轮只补这些安全字段与前台变化事件，对比冷启动第一次请求、点击桌面浮窗、再次选择同一项；继续保留一次正常尝试策略。

本阶段尚未采纳覆盖 composer 聚焦期的租约。后续已接受 [0050](../adr/0050-hold-the-host-focus-for-the-composer.md)，但它仍不能保证第一次聚焦取得前台，不能代替此项诊断。

后续准备被动诊断 0.6.0，在 `ForegroundLease.Take` 现有 `SetForegroundWindow` 调用旁插入参数和返回值读取，保留原调用、次数与返回值。记录目标及前台 HWND/PID/class、调用线程焦点、最后输入 tick，并用进程外前台事件关联变化。没有增加前台操作、输入合成或重试，产物仅构建，尚未安装。

隔离检查直接编译生产 `ForegroundLease`，将其 Win32 操作换为固定状态，并在游戏同款 Unity Mono 上运行相同 Harmony 插桩。原生返回值为 false、true、false 的三种情形，原 `Take` 结果分别为 false、true、true；最后一种在调用前就已是目标前台。每种恰好调用一次原函数，额外前后钩子同时存在时结果也相同。该检查没有真实改变前台。

另由电脑操作工具正常激活现有窗口，独立观察器在安装线程的消息泵内收到三次真实前台事件，随后在同一线程成功解除。它验证了新记录器的回调路径，没有复现真实 XSOverlay 的首次切换失败，也没有验证 Unity 主线程在实际游戏中的事件覆盖和退出清理。

原生返回值、即时快照与前台事件应共同解释，不能把一个 false 直接当作权限拒绝。[GetLastInputInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo) 不标识输入接收进程，也不保证 tick 严格递增。事件可能延迟回调，查询到的 PID/class 只代表回调时状态；超过首次尝试后三分钟或发生丢记录时，缺少事件不能用来证明没有前台切换。
