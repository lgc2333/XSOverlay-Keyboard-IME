# 修饰键的粘滞归页面，切输入法前先上屏

[0036](./0036-one-table-for-key-ownership.md) 把组字期间的单按 Shift 与 Caps 交给了输入法。真机测下来两件事不对：

- CapsLock 在输入框里打不出大写，按过之后也取消不掉；Shift 的粘滞被打断，组字时没法再打大写字母。
- Win+空格 快速切换输入法时状态会乱：旧输入法还持有的组字会跟到新输入法里。

原因是同一个：页面把修饰键**同时**当成「输入法的一下按键」和「页面自己的粘滞状态」。两个写者，状态必然对不上。

本决定：**粘滞状态只归页面；切换输入法前先把组字上屏。**

1. 页面发来的 Sticky（Shift、Ctrl、Win）与 Toggle（Caps）**一律留在页面**，插件不吞也不喂。页面记下这一下，之后每一个字母的 `webValue` 都带着 shift 或 caps，插件把那个大写字母当字符送进输入法——组字里自然就是大写。
2. 这一条之外的一切仍按 [0036](./0036-one-table-for-key-ownership.md) 的表走。
3. 喂 Win+空格 之前，如果输入法还持有组字，**单独**送一次 Enter 把它上屏；等约 60 毫秒再切。两次按键不能挤在同一批：TSF 的结束回调是异步的，旧组字的清理可能扫到新内容。
4. 从 Enter 到新输入法稳定之前，**不把前台还回去**。Rime 失去前台会直接 `_AbortComposition`，焦点来回跳本身就是组字被打断的原因。

## Considered Options

- 两边都给（页面记粘滞，插件同时喂 Shift）：一个按键两个主人，Rime 收到 Shift 就原样上屏，正好抵消想打大写的目的；否决。
- 只喂输入法、页面不要粘滞（[0036](./0036-one-table-for-key-ownership.md) 的原样）：真机打不出大写、锁不住也解不开 Caps；否决。
- 切输入法时不处理组字：实测旧组字会跟过去，用户看到的是串味；否决。
- 粘滞留页面，切换前先上屏：采纳。

## Consequences

- Rime 的「组字中按 Shift 原样上屏」不再触发，因为 Shift 根本不到输入法。要原样上屏，用 Esc 或语言栏镜像切换键。
- CapsLock 重新由页面与系统负责：能打出大写，也能再按一次取消。
- Win+空格 在组字中途按下时，会先把正在组的内容上屏再切换；上屏的文本算旧输入法的提交。
- 页面上的粘滞状态与游戏的按键状态是同一个来源（游戏自己维护的 latch），插件不再参与判断。
- 插件在所有喂键路径上都会 `AttachThreadInput`，而该调用会重置 `GetKeyState`/`GetKeyboardState` 看到的状态。这是 Caps 与修饰键状态异常的强嫌疑，也是本决定干脆不喂 Caps 的理由之一；以后若要再碰修饰键，先量这个。
