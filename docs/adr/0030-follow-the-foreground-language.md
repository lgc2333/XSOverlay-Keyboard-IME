# 组字线程跟随前台窗口的输入语言

[0009](./0009-profile-scope.md) 把输入法的枚举与切换限定在插件自己的线程：界面显示的「当前输入法」只代表组字线程，可能与用户在系统里看到的默认输入法不同。真机上这条后果就是一个 bug：用 Win+空格 换到别的输入语言后，组字线程还留在原来的语言上，键盘上画的仍是前一个输入法的图标与名字。

Win+空格 只切**前台窗口那条线程**的输入语言，档案按线程保存。插件不能替用户按这个键，也读不到别的进程的 TSF 状态。所以本决定：**组字线程跟随前台窗口的输入语言，与前台是不是游戏无关。**

- 自己的线程：`WM_INPUTLANGCHANGE` 是窗口消息，宿主窗口本来就有消息泵，语言一变就到，不用轮询。
- 前台窗口：Windows 不提供跨进程的通知，只能轮询 `GetKeyboardLayout(GetWindowThreadProcessId(GetForegroundWindow()))`，挂在现有的 400 毫秒定时器上。前台是浏览器、桌面，都一样跟。
- 语言一变：用 `ITfInputProcessorProfiles::ActivateLanguageProfile` 把本线程切到该语言的默认档案，重开语言栏项，重读输入法名字推给页面。
- 组字中不切：切换档案会让输入法丢掉正在进行的组字，所以只在没有活组字时跟随。

## Considered Options

- 只刷新显示，不跟随：组字线程压根没变，图标与名字还是前一个输入法的，等于没修；否决。
- 键盘页打开期间一直持有前台，让系统把切换落到插件线程：能工作，但插件会在 VR 键盘打开时占着系统输入状态，还牵连游戏自身的焦点；否决。
- 通过主线程泵去问游戏线程的 TSF 状态，连同一语言下的两个输入法也分得开：最完整，但要在 Unity 主线程上碰 TSF，脆弱且未验证；否决。
- 前台布局轮询加本线程回调：采纳。

## Consequences

- 只跟到语言这一层：HKL 分得出 zh-CN、en-US、ja-JP，分不出同一语言下的两个输入法（小狼毫与微软拼音）。那一对切换靠「该语言的默认档案」的名字变化发现，而默认档案不一定是本线程真正在用的档案：二者一致时显示与组字都对，不一致时显示会先跟上名字，组字仍用原档案。这是读不到活动档案的代价，见 [0009](./0009-profile-scope.md)。
- 跟随就是替用户切档案：`ActivateLanguageProfile` 会重新激活输入法，而中英状态按输入上下文各自保存，因此切换后从英文开始。这与用户自己按 Win+空格 的观感一致，但插件确实动了档案。
- 前台是桌面上的其他程序时也跟：VR 键盘会跟着用户当前看的窗口换语言。
- 组字期间不跟：此时前台通常是插件自己的宿主窗口，本来也不会变。
- 轮询在输入法档案没变时只读一次布局句柄与一次档案名，代价可以忽略；档案变了才做一次 COM 激活。
- 语言没有文字服务可描述时（传统键盘布局，如美式键盘），显示退化为该语言自己的名字，而不是停在旧输入法的名字上。
